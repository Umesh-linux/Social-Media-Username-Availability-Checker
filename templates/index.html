Hash Table Execution Pipeline

Search Complexity: O(1) Average
1
Input Normalization: Input username string is trimmed and converted to lowercase: username.strip().lower() to guarantee case-insensitive uniqueness.
2
DJB2 Rolling Polynomial Hash: Initial prime seed 5381 is shifted left by 5 and added to hash: ((hash << 5) + hash) + ord(char).
3
Modulo Bucket Index Mapping: 32-bit integer is distributed across table slots using modulo arithmetic: bucket = hash % 10007.
4
Step 4 – Username Availability Lookup: The system calculates the bucket index and searches the corresponding chain to determine whether the username already exists. Lookup is O(1) average under suitable hashing and load-factor conditions, with O(n) worst-case complexity.
5
Separate Chaining Resolution: If two usernames hash to the same bucket index, they are safely appended as a linked-list node in that bucket without overwriting.
6
Dual-Layer Storage & Bcrypt Security: Saves credentials permanently in SQLite with Bcrypt (cost 12) while maintaining the high-speed in-memory hash table in sync.

📐 Academic Load Factor (α) Proof

The load factor $\alpha = \frac{N}{M}$ measures how full the hash table is. In our production configuration with $M = 10,007$, the load factor remains small ($\alpha \ll 0.75$), guaranteeing that average bucket chains contain fewer than 2 elements. This mathematically verifies the constant time search performance $O(1)$.
